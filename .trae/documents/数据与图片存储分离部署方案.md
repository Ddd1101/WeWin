# WeWin 数据与图片存储分离部署方案

## 1. 目标和部署拓扑

应用运行在阿里云马来西亚地域。网络波动分为两段，分别测量用户到阿里云 HTTPS 入口的链路，以及马来西亚 ECS 到 n1 的存储链路。n1 所在位置、运营商和链路质量以实测为准。

| 部署条件 | 存储安排 | n1 断线时的业务表现 |
| --- | --- | --- |
| 容许主库和在线媒体存放在阿里云，优先保证业务连续性 | **推荐。** 主库与 Django 同地域部署。初期可沿用 ECS 上的 SQLite 和本地媒体盘，按容量与并发需要再迁至同地域数据库和 OSS。数据库快照与媒体异步同步到 n1。 | 业务仍在马来西亚侧读写，备份延迟上升，链路恢复后补传。用户到马来西亚入口的网络仍需单独验证。 |
| 主库和媒体必须放在 n1 | 采用下方 frp + MariaDB + SSHFS 拓扑。先用实际用户和真实链路验证请求延迟与可接受停机时间。 | 静态页面可打开。依赖数据库的登录、商品和订单接口，以及依赖 SSHFS 的图片，按各自依赖失败并在链路恢复后恢复服务。 |

以下 n1 在线存储设计适用于第二种部署条件。frp 承载数据库和 SFTP 连接，SSHFS 将 n1 的图片目录挂载到阿里云。Django 继续通过 `ImageField` 和相对路径读写文件，Web 和 Android 继续使用现有的 API 路径及图片字段。

```text
Web / Android → HTTPS :443 → 阿里云 Nginx
  /        → Page/dist
  /api/    → Gunicorn 127.0.0.1:8003
  /media/  → /mnt/wewin-media

Gunicorn 和拉单进程 → 127.0.0.1:13306 → n1 MariaDB 127.0.0.1:3306
/mnt/wewin-media    → 127.0.0.1:10022 → n1 SFTP /srv/wewin/media

n1 frpc → 主动连接阿里云 frps :7000，承载数据库和 SFTP 映射
```

| 位置 | 服务和端口 | 存储 |
| --- | --- | --- |
| 阿里云（2 vCPU / 2 GB / 40 GB，x86） | Nginx 公网 `443`。如需证书签发或 HTTP 跳转则开放 `80`。frps 接入端口 `7000`。Gunicorn 和 frp 映射端口仅监听回环。 | 应用、前端构建产物、部署配置和日志。 |
| n1（Armbian / ARM / 128 GB） | frpc 主动出站。MariaDB 回环 `3306`，frpc 通过本机 `22` 转发 SFTP。 | MariaDB 数据目录、`/srv/wewin/media`、本机备份暂存区。 |
| 独立备份位置 | 由部署方选定并验证恢复权限。 | 同一批次的数据库备份、媒体文件和校验清单。 |

这套拓扑把数据库和媒体的在线可用性绑定到 n1 及其网络。n1 或隧道故障时，阿里云仍可返回前端静态页面，业务 API 和媒体访问按各自依赖返回明确错误。初次实施用真实链路演练决定是否接受停机时间和请求延迟。

| 项目 | 当前状态及影响 |

当前仓库的 SQLite 快照约 **24.7 MiB**，有 1,328 个商品、9,921 条 SKU、2,205 个订单、2 个客户。数据库中有 **9 条非空商品图片路径**，本地媒体目录找不到对应文件。正式迁移以线上冻结时生成的快照和媒体清单为准，逐条记录源文件缺失情况。

按原方案将 SQLite 快照导入空 SQLite 库时，核对的图片路径、金额、订单 JSON 和 BOM 快照一致。默认 JSON 序列化精确到毫秒，演练中 1,327 条商品创建时间丢失亚毫秒精度。更新后的自然键导出命令也已在 Django 5.2.19 和临时 SQLite 库验证，10 张业务表的主键集合一致，外键检查通过。目标 MariaDB、frp 和 SSHFS 尚需现场验证。 [Django JSON 序列化](https://docs.djangoproject.com/en/5.2/topics/serialization/#djangojsonencoder)

## 3. 实施改动

### 3.1 公网入口和客户端切换

- 使用系统 Nginx 管理 WeWin 站点，静态目录由 Nginx 用户读取。站点配置包括 SPA 回退、`/api/` 反代和独立的 `/media/` 路由。`proxy_pass` 保留 `/api/` 前缀。转发外部请求的 `Host`，由 Nginx 覆盖 `X-Forwarded-Proto`，由 Django 信任这个受本机反代控制的头。生产环境配置 `DEBUG=False`、准确的 `ALLOWED_HOSTS` 和稳定的 `SECRET_KEY`。需要保留 Django Admin 时，同时配置 `/admin/`、`collectstatic` 产物与访问范围。
- 媒体路由使用 `location ^~ /media/` 和 `alias /mnt/wewin-media/;`，缺失文件返回 404，避免进入 SPA 回退。当前 `nginx_system.conf` 中有图片后缀正则，普通前缀会被正则覆盖。目录浏览关闭。若商品图片允许凭 URL 访问，Nginx 可直接提供文件。若必须沿用企业级访问控制，先补经授权的媒体访问链路，再开放图片入口。放行直出时只允许可安全展示的图片格式，按实际内容校验上传，禁用浏览器 MIME 嗅探。 [仓库 Nginx 配置](../../nginx_system.conf) · [Nginx 路由匹配](https://nginx.org/en/docs/http/ngx_http_core_module.html#location)
- Web 生产构建默认使用同源 API，统一调整 API 基址和登录、注册等直接调用基址的入口，本地开发继续支持指定后端地址。Android 使用新的 HTTPS `API_BASE_URL` 重新构建发布，真机验证登录、商品图片和上传。当前地址编进 APK，旧包不会随服务器切换自动更新。关闭旧公网入口前，确认受影响客户端已完成切换，或提前确定临时受控兼容入口及退役日期。 [Web API 基址](../../Page/src/api/config.js) · [登录与注册 API](../../Page/src/api/account.js) · [Android 构建配置](../../Android/app/build.gradle.kts)

### 3.2 frp、MariaDB 和后端配置

- frps 与 frpc 使用经过演练的同一版本。frps 设置 `proxyBindAddr = "127.0.0.1"`，用 `allowPorts` 只允许 `13306` 和 `10022`，并要求客户端鉴权与 TLS。frpc 验证服务端证书。阿里云安全组在 n1 出口地址固定时限制 `7000` 的来源。上线前从阿里云本机验证两个映射可用，从外部验证两个映射端口均不可达。 [frp 服务端配置](https://gofrp.org/en/docs/reference/server-configures/) · [frp 客户端鉴权](https://gofrp.org/en/docs/features/common/authentication/)
- n1 上 MariaDB 保持监听 `127.0.0.1:3306`，frpc 的 MariaDB 代理指向该地址，映射到阿里云 `127.0.0.1:13306`。数据库使用 `utf8mb4`，启用严格 SQL 模式。应用账号只授予业务库所需的读写权限，建表和迁移使用单独账号。演练时验证所选排序规则对货号、用户名和企业名称的大小写、尾随空格与唯一性的影响。MariaDB 的 JSON 类型以 `LONGTEXT` 实现，验收按反序列化后的内容比较。 [MariaDB JSON 类型](https://mariadb.com/docs/server/reference/data-types/string-data-types/json)
- Django 读取 `DB_ENGINE/DB_NAME/DB_USER/DB_PASSWORD/DB_HOST/DB_PORT`、`MEDIA_ROOT` 和 `MEDIA_URL`。本地开发默认 SQLite 和 `Server/media`。生产配置明确选择 MariaDB，环境变量缺失时报配置错误。生产 `MEDIA_ROOT=/mnt/wewin-media`，`MEDIA_URL` 指向正式 HTTPS 入口的绝对 `/media/` 地址，确保商品和 BOM API 返回的图片地址都能被两个客户端解析。现有相对文件名可直接迁移。
- 数据库驱动在运行 Django 的阿里云 x86 节点安装，采用 Django 官方支持的 `mysqlclient`。当前 Django 4.2.30 已结束扩展支持。计划在 SQLite 上独立验证并升级至受支持的 Django 5.2 LTS 补丁版本，再在目标 MariaDB 上演练。根据目标系统实际可安装的 MariaDB、Python 和客户端库选定兼容版本并记录在部署清单中。 [Django 4.2 支持公告](https://www.djangoproject.com/weblog/2026/apr/07/security-releases/) · [Django 5.2 数据库支持](https://docs.djangoproject.com/en/5.2/ref/databases/)

### 3.3 SSHFS 挂载与文件写入

1. n1 创建专用 SFTP 账号，使用独立密钥且仅授权媒体目录。阿里云通过 `127.0.0.1:10022` 挂载到 `/mnt/wewin-media`，固定 n1 SSH 主机密钥，并为 SSH 设置连接超时和 keepalive。用 systemd 管理挂载，配置断线恢复与有界重试，在实际 Linux 环境测量 I/O 失败和恢复时间。
2. 按实际 Linux 用户和组映射文件权限。以 Gunicorn 用户验证读、写、重命名和删除，以 Nginx 用户验证只读。裸挂载目录由 root 持有并禁止应用写入。挂载后以能够实际读取远端目录中的探测文件判定可用，单看目录存在或单元状态可能漏掉已失联的挂载。
3. 依赖媒体的上传、替换和移除在挂载失效时返回可重试错误。替换时先保存新文件，提交数据库引用后再清理旧文件。若数据库写入失败，保留旧引用及旧文件，记录新文件以便清理。对并发替换序列化同一商品的更新，删除失败由后续核对任务处理。以生产后端校验图片内容和单文件大小，Nginx 的请求体上限同时为 multipart 字段留出余量。 [商品更新逻辑](../../Server/store/views/product_views.py) · [上传大小设置](../../Server/wewin/settings.py)
4. 预同步源媒体目录时保留相对路径，停写后再同步增量。对比每个数据库引用的文件是否存在，并校验已复制文件的大小与哈希。源端已缺失的文件单独列清单，恢复或确认其处置后再接受该批次。

### 3.4 Gunicorn、调度和运行探测

- Gunicorn 监听 `127.0.0.1:8003`，由 systemd 以应用账号运行。单元配置绝对 `ExecStart`、`WorkingDirectory`、环境文件和失败重启策略。2 GB 机器从 2 个 worker 开始，通过业务负载下的内存和延迟决定是否调整。生产环境统一由 systemd 管理启停，避免旧脚本通过 `pkill` 影响新进程。
- 将 `auto_pull_orders` 移到独立的 Django 管理命令和单独的 systemd 单元。Web worker、迁移和 CLI 初始化不再启动调度。单台阿里云只运行一个调度实例，部署窗口可单独停止。断线恢复后，核对下次拉取时间和停机期间的订单，按需用现有拉单入口补拉。 [调度实现](../../Server/store/apps.py) · [拉单时间窗口](../../Server/store/tasks.py)
- 分别监测进程存活、经 Django 实际配置的数据库查询、媒体读探测和定期写探测。探测状态对外只返回是否可用，依赖异常及恢复写入服务端日志。为数据库连接和读写、SSH 探测和反代设置超时，验证失联时相关 API 返回 503、静态首页仍可加载，避免耗尽 Web worker。用同一批商品列表、成品 BOM 和订单请求记录切换前后的延迟和错误率。性能门槛以实际客户端超时和演练基线确定。 [商品列表查询](../../Server/store/views/product_views.py) · [Web 请求超时](../../Page/src/api/client.js)

### 3.5 马来西亚链路波动与恢复

1. **分别测量两段链路。** 在日常和高峰时段，从实际用户网络测 HTTPS 登录、商品列表和图片预览，从马来西亚 ECS 测 frp 重连、复用连接的数据库查询、媒体读取及上传。记录 P50、P95、超时率、断线时长和恢复耗时。用相同数据比较云侧本地库与 n1 库，特别关注商品列表和 BOM 的多次往返。以 Web 当前 10 秒请求超时作为上限约束，另定更短的交互延迟目标。 [Web 请求超时](../../Page/src/api/client.js) · [商品列表查询](../../Server/store/views/product_views.py)
2. **优先让跨地域同步退出请求链路。** 选择云侧主存储时，以异步任务同步数据库备份和媒体，每批校验后再标记成功，失败保留上一个完整批次。告警按最后一次成功备份的时间及待同步文件积压触发。ECS 现有磁盘要核对媒体增长和备份暂存所需空间。改用 OSS 时优先选择 ECS 同地域的内网端点供应用访问，并按图片权限要求选用对客户端可达的访问方式。 [阿里云 OSS 地域与端点](https://www.alibabacloud.com/help/en/oss/user-guide/regions-and-endpoints)
3. **主存储在 n1 时，超时、重连和重试分别处理。** frp 由 systemd 管理，验证抖动时重连及告警。数据库开启连接、读写超时；若复用持久连接，启用 Django `CONN_HEALTH_CHECKS` 并实测开销。SSHFS 配置 keepalive 和重连，验证旧句柄失效及上传中断的处理。只读请求可在总超时内做有限重试；写入响应超时时先查询实际状态，结果无法确认的写入只在有幂等保障后重试。长时间断线进入维护或按依赖返回 503，主库恢复后重建连接并验证实际读写。主库在任一时刻只有一个写入点。 [Django 连接管理](https://docs.djangoproject.com/en/5.2/ref/databases/#persistent-connections) · [SSHFS 断线行为](https://manpages.debian.org/experimental/sshfs/sshfs.1)
4. **恢复后按成功水位补拉。** 云侧存储与 n1 同步恢复后只补传缺失批次。n1 主库存储恢复后，按店铺从最后确认成功的拉取区间补拉订单，核对任务结果及去重。当前任务按配置间隔向前取时间窗，并在失败后也更新调度时间，长断线结束后需要显式补拉。 [自动拉单逻辑](../../Server/store/tasks.py)

上线演练覆盖高延迟、短时丢包、持续断线及恢复，尤其验证上传中断、写入已提交但响应丢失、断线跨过一个拉单周期三个场景。只有业务延迟、断线影响和恢复耗时都达到事先认可的指标，才把 n1 作为在线主存储。

## 4. 迁移与切换

本节 MariaDB 与 SSHFS 切换步骤用于 n1 在线主存储。若选择云侧主存储，先保留现有业务库和媒体位置，验收马来西亚入口及跨地域备份恢复，再分别安排数据库或媒体迁移。

### 演练

1. 盘点线上运行入口、SQLite 文件、媒体目录、自动拉单状态、客户端版本和 Django 管理功能的实际使用情况。确定停写窗口、发布版本、备份位置、恢复时间目标，以及图片公开访问和缺失图片的处置方式。仓库也跟踪了 SQLite 文件，发布应用时将线上库和媒体保留在独立位置，避免被检出或刷新源码覆盖。
2. 用 SQLite 在线备份生成源快照，并将数据导出文件放在权限受限的临时目录。用部署版本、目标 MariaDB 空库及实际隧道执行 `migrate` 和 `loaddata`。导出、建表、导入分别用独立进程，把各自的源库或目标库配置成 Django 的 `default`。历史 SKU 数据迁移直接用默认管理器访问模型。 [SQLite 备份](../../Server/backup_db.py) · [历史 SKU 数据迁移](../../Server/store/migrations/0012_product_sku.py)
3. 导出时排除由 `migrate` 重建的 `contenttypes` 和 `auth.permission`，并使用 `--natural-foreign` 序列化对它们的引用。保留业务主键。根据线上实际使用情况验证用户、用户组、权限关联和 Django Admin 日志。若源库有自定义权限，显式迁移并验证引用。确认默认 JSON 对时间戳的精度损失是否可接受。需要保留微秒时，先验证可保留微秒的导出与导入方式。 [Django 自然键](https://docs.djangoproject.com/en/5.2/topics/serialization/#natural-keys)
4. 校验各业务表行数及关键主外键，比较价格与金额、订单 JSON、BOM 快照、时间及企业归属。用不同企业和管理员账号验证权限。在演练库验证新建记录不会与迁入主键冲突，并覆盖订单拉取、商品与 SKU 编辑、图片上传替换和客户端访问。记录演练耗时、故障恢复时间及可接受的差异。用原 SQLite 和原媒体目录演练回退，同时验证新版 Web、Android 继续经同一 HTTPS 入口访问。

迁移命令在 `Server/` 下运行。以下命令适用于已接受默认 JSON 时间精度、权限数据已完成核对的迁移批次。`$fixture_path` 指向仓库外权限受限的文件，数据库环境随命令单独加载。

```bash
# default 指向源 SQLite 快照
python manage.py dumpdata --natural-foreign \
  --exclude contenttypes --exclude auth.permission --output "$fixture_path"

# default 指向空的目标 MariaDB，使用迁移账号
python manage.py migrate --noinput
python manage.py loaddata "$fixture_path"

# 切换到生产运行账号，显式检查生产配置及数据库
python manage.py check --deploy --database default
```

### 正式切换

| 顺序 | 操作 | 继续条件 |

## 5. 回滚、备份与验收

### 回滚和恢复

- **开放新库写入前**，切回已演练的 SQLite 兼容版本，指向冻结的 SQLite 和原媒体目录。在同一个 HTTPS 入口验证 Web 和新版 Android 的登录、商品和图片，再恢复写入及调度。需要继续服务的旧版客户端，沿用演练时确认的入口安排。
- **开放新库写入后**，先暂停写入和调度，保存 MariaDB 和媒体现场。优先修复连接、挂载或应用配置。若必须退回 SQLite，先核对新库新增、更新和删除的记录及图片，演练回迁或按批准的范围补录，再恢复流量。旧库快照缺少切换后的修改。
- 正式备份保存 MariaDB 逻辑备份、媒体文件和校验清单。初期在可接受的短暂停写窗口内生成同一批次的数据库和媒体备份，并复制到 n1 之外。备份频率、保留期限和可接受的数据丢失时间按实际业务确认。恢复演练在隔离环境同时还原库与媒体，验证商品和 BOM 引用、图片读取和权限。

### 上线验收

按所选拓扑执行。云侧主存储沿用 SQLite 时，数据库项改为验证 SQLite 快照与恢复，frp 和 SSHFS 项改为验证实际使用的备份传输链路。

- [ ] 目标 MariaDB 上的迁移、数据核对、主键分配和权限验证通过。
- [ ] Web 和 Android 真机通过 HTTPS 登录并完成商品、订单和报价的关键操作。旧入口按约定处理。
- [ ] 商品列表、详情及 BOM 图片 URL 指向预期入口。上传、替换和移除反馈正确，n1 上的文件和数据库引用一致，缺图按清单处置。
- [ ] frp 映射仅监听阿里云回环。阿里云或 n1 单独重启、隧道运行中断开和媒体卸载后，服务能恢复或给出明确故障。媒体失联期间没有文件落入本地裸挂载目录。
- [ ] 多个 Gunicorn worker 运行时只有一个自动拉单实例，短时停机后的订单可按验证过的流程补拉。
- [ ] 实测页面/API 延迟、切换窗口和备份恢复时间符合演练前确认的目标，数据库和媒体的联合恢复已验证。
- [ ] 分别验证用户到马来西亚入口、马来西亚到 n1 的高峰期延迟和断线恢复。采用云侧主存储时，验证 n1 断线期间业务仍能读写，恢复后备份可以补传和还原。
